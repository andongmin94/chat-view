## 현재 위치와 완료 기준

`[x]`는 명시한 좁은 개발 범위와 실제 근거다. 실계정·물리 투컴·배포 완료와 다르며 체크 개수로 완성도 비율을 계산하지 않는다.

기존 native 관리 버튼 → 시스템 브라우저 → 치지직 신원 확인 → 채널 확인 → 원래 관리 페이지를 유지한다. 이번에는 쿠키와 헤더를 HTTP 도구에서 직접 넣는 대신 실제 Chromium이 생성하는 요청으로 관리 페이지 세 곳의 복구·계정 전환·취소·뒤로가기와 앱 로그인 요청의 브라우저 승인 단계를 확인했다. 제공자 화면/API는 합성이며 native 실행 파일에서 브라우저를 여는 전체 통합 검사는 아니다.

정상 HTML 로그인 폼이 403으로 거절되는 제품 결함을 재현하고 수정했다. 폼 문서는 `Referrer-Policy: same-origin`으로 실제 Origin을 보내며, 정확한 Origin/CSRF 검사는 유지한다. null/누락/외부 Origin을 허용하는 대체 경로는 없다. 콜백 리디렉션·오류 문서는 `no-referrer`를 유지해 코드/state가 담긴 query를 다음 페이지에 전달하지 않는다. 외부 제공자 화면으로 Referer나 native Authorization이 전송되지 않는 것도 브라우저에서 검사했다.

인증 후 cross-site로 분류되는 복귀는 회전된 동일 브라우저 쿠키에 묶인 정확한 다음 페이지의 top-level GET 한 번만 허용한다. 최대 30초이며 기존 인증 요청 만료를 넘지 않는다. 다른 페이지·iframe/fetch·POST·query·기존 쿠키에는 적용하지 않는다. 관리 채널 확인과 PC 역할 승인은 별도로 눌러야 한다. 취소 후 뒤로가기로 소비된 확인 페이지를 다시 열면 403 차단은 유지하면서, 신원·폼·권한 없는 다시 로그인 안내를 표시한다.

브라우저 복구/계정 전환은 기존 native 승인·역할·캠페인·저장 grant를 새로 만들거나 교체하지 않는다. 만료된 변경 요청을 재로그인 뒤 자동 재실행하지 않는다. 브라우저 관리 계정과 앱 계정은 자동 일치를 보장하지 않으며, 브라우저 창은 HUD 캡처 보호 밖이다.

**다음 흐름:** **D4의 기존 캡처 시험 Q4/Q5 종료·취소·설정 복원 순서**를 읽고, 시험 중 닫기/실패/종료에서도 시험용 상태가 남지 않고 원래 사용자 설정으로 돌아오는 경로를 기존 UI에서 완성·검증한다. 새 인증/기기등록 제품이나 별도 보고서를 만들지 않는다. 실계정·실서비스 HTTPS·물리 영상은 별도 미완료이며 독립 구현을 막는 이유로 사용하지 않는다.
