## 현재 흐름: 송출 승인 충돌 → 기존 연결 해제 → 원래 요청 승인

시작 HEAD `acbfae3eb0e49b771fb5d966b7f9ea1baab93971`에서 AGENTS → PRODUCT → development-workflow → architecture → 이 문서를 순서대로 읽었다. 직전 플랫폼 #66/run `38069340404`의 5개 job 성공을 재확인했다. 이전 코드의290/290·Chromium13/13을 이번 실행으로 계산하지 않는다.

### 구현

- 기존 `/login/:id/approve`에서 송출 승인이 이미 있으면 HTTP409를 유지하면서 같은 브라우저의 관리 채널·기존 송출 연결·해제 영향을 보여준다. 기존 `/account#approved-connections`와 연결별 CSRF 해제 form을 재사용한다. 조회/충돌 자체는 권한·광고 선택·채팅을 바꾸지 않는다.
- 해당 브라우저에만 원래 요청 ID를 잠시 기억하고 계정 화면에서 확인 번호와 원래 승인 화면으로 돌아가는 링크를 제공한다. 링크는 권한이 아니며 요청의 pending 상태를 매번 재확인한다. 계정 전환·로그아웃은 문맥을 폐기하고, 취소·승인 완료·만료된 요청은 복귀 링크를 남기지 않는다. 종료된 요청의 GET은 상태409/410과 재시작 안내를 주며 승인 form을 표시하지 않는다.
- 사용자가 기존 송출 연결만 해제한 뒤 원래 요청의 채널·역할을 다시 직접 승인한다. 게임 채팅·다른 계정·기존 공개 URL은 유지한다. 새 승인/출력 보고로 시험 광고를 자동 재선택하지 않는다. 기존 승인 점유 여부를 `ensureChat` 대기 뒤에도 재확인한다.
- 새 엔드포인트·의존성·DB 스키마·역할 자동 이전·게임 PC OBS 요구는 없다. 네이티브 HUD/WGC·공개 배너 렌더러·회계·시간/픽셀 한도·workflow는 변경하지 않는다. 두 신규 요청이 모두 승인된 뒤 앱 응답 수집에서 경쟁하는 경우는 아래 다음 흐름이다.

### 검사

- 로컬 Node22.16.0: 원격 blob SHA와 일치시킨 원본에서 변경했다. 변경 MTS 문법, Python 컴파일, 공백 검사를 통과했다. 실제 생산 메서드의 경계 검사 **7/7**은 소유자별 충돌/단순 안내·게임 역할 비대체·취소/만료·예외 전파와 테스트 시계 동작을 확인했다. 협력 객체 대역을 쓴 좁은 검사이며 전체 서비스/SQLite/ws/Chromium 검증은 아니다. 컨테이너의 GitHub DNS 접근이 실패해 전체 checkout/의존성 설치는 실행하지 못했다.
