### 변경한 동작

- 기존 `DisplayClient`의 **세션 승인 갱신 401/403 → Denied**를 받은 때만 마지막 승인 거부 이유를 기록한다. 소켓 단절·재연결·일반 오류를 철회로 단정하지 않는다. 승인 보유/폐기와 갱신은 기존 클라이언트가 계속 책임지며 새 인증·통신·기기등록 체계를 추가하지 않는다.
- 채팅창의 기존 세션 영역은 접속 수를 **현재 확인되지 않음**으로 지우고 **이전 채팅 승인: 서버 거부 · 복귀 불가 / 로그인·연결에서 다시 승인**을 표시한다. 창 재열기, 영상창 왕복, 중지·실패한 복귀 명령으로 이 이유가 사라지지 않는다. 기존 복귀 버튼은 비활성이고 영상창의 기존 읽기 전용 상태도 미연결을 표시한다. 새 명시적 연결 요청이 실제로 시작된 때 이전 거부 이유를 지우며, 이것을 새 승인 완료라고 표시하지 않는다.
- HUD 상태는 로그인 필요로 전환한다. 개인 채팅 텍스트·서버 소켓 수를 지우고 자동 연결 예약을 폐기하지만, **선택 게임 창의 WGC·출력 HWND·시험 패턴 동의·검정 덮개를 조작하지 않는다.** 영상 중지는 기존 버튼으로 별도 수행하고, 영상 재개에는 새 시험 패턴/수신 확인이 필요하다. 기존 HUD/설정창 보호 실패의 검정 차단은 그대로 우선한다.

### 이번 검사와 판정 경계

- **로컬:** 원격 blob과 일치시킨 소스에서 실제 안내 함수 및 Denied 분기 본문을 추출한 C++20 대역 검사 **GCC89/89, Clang ASan+UBSan89/89 통과**. 12개 기존 상태·종료 우선권·알 수 없는 접속 수·단순 연결 오류와 승인 거부 구분을 확인했다. 새 연결 시작 뒤에만 이유를 초기화하는 순서와 Node22 `.mts` 문법, diff 공백 검사도 확인했다. 실제 WinHTTP/Win32/WGC 실행 근거는 아니다.
- 기존 `companion-chat-video`의 모든 중지/복귀·다른 창 선택·DOM 문자열·출력 픽셀 조건은 **return 모드**에 유지한다. 동일 실행 파일/driver의 **revoked 모드**를 새 CTest `chat-view-companion-chat-revocation`으로 연결한다. 독립 로그인 시스템이나 캡처 구현을 복제하지 않는다.
- 새 흐름은 실제 HUD/WebView2·WinHTTP·HTTP/SQLite/WebSocket·WGC를 연결하고, 기존 서버 `removeConnection`에서 해당 승인만 제거한다. 기존3회 명시적 복귀 이후 서버가 정확히1회 갱신을 거부해야 하며, 두 패널 왕복/복귀 클릭/영상 재시작은 **새 로그인·다른 저장 계정 사용·추가 갱신**을 일으키면 실패한다. 첫 채팅 DOM의 실제 행 제거, 최신 계정 페이지 승인0/소켓0과 네이티브의 접속 수 미확인 표시, 다른 계정의 DPAPI/서버 승인 보존도 확인한다.
- 선택된 합성 게임 창은 기존 애니메이션 모드로 계속 새 프레임을 만든다. 철회 전후 같은 출력/덮개/대상과 선택 세대, 증가한 실제 프레임 및9개 출력 픽셀을 요구한다. 그 뒤 명시적 중지의 검정 픽셀, 과거 동의 재사용 거부, 새 패턴 확인 뒤 영상만 재개를 검사한다. 정지 소스의 정상적인2초 프레임 만료를 철회 실패로 오인하지 않는다.
- 제공자·출력 사각형·물리 수신자의 동의는 fixture 입력이다. 실제 출력 topology를 우회하는 생산 옵션은 없다. 기존42개 CTest와 제한은 유지한다. 추가 검사는 기존 통합 검사와 동일한 CTest60초/driver45초, 첫 프레임10초·중지2초·RGB오차8을 사용한다. 아래 Windows 결과와 로컬 대역 검사를 구분한다.
