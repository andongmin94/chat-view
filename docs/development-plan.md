## 현재 흐름: 취소 미확인 옛 브라우저 요청 ↔ 새 게임/송출 로그인 번호 대조

### 구현

- 브라우저 `/login/<id>`의 **아직 대기 중인 요청**에 해당 페이지의 확인 번호, 앱의 **현재** 확인 번호·역할과 일치해야 한다는 경고, 일치하지 않으면 **이 요청 취소**를 누르라는 안내를 명시한다. 브라우저는 네이티브 앱의 현재 상태를 알 수 없으므로 이를 현재 요청이라고 단정하지 않는다. 기존 CSRF·Origin·쿠키 권한과 확인 번호/역할의 불변 조건은 그대로다.
- 앱에서 서버 취소가 **미확인**이면 최근 중지한 공개 6자리 확인 번호를 별도의 보호된 연결창 행에 남긴다. 사용자가 로그인 / 연결을 명시적으로 다시 누른 때에는 **현재 번호**를 따로 표시하며, 옛 번호의 페이지에서 승인하지 말고 직접 취소하도록 안내한다. 취소 결과가 확인된 경우 옛 번호를 남기지 않는다. 첫 화면에서 중지해 번호를 받은 적이 없으면 임의의 번호를 만들어 표시하지 않는다.
- 중지 후 새 연결을 시도할 때 `이 PC에서 연결 유지` 선택이나 다른 DPAPI 저장 승인 때문에 새 브라우저 동의를 건너뛰지 않도록 `force_new_login_` 경계를 둔다. 성공적으로 새 역할·채팅 승인을 수신했을 때만 해제한다. 새 HTTP 요청, 관리자 권한이나 provider account picker는 만들지 않는다. 종료·로그아웃·영상 시작·광고 선택을 자동 실행하지 않는다.
- 원래 브라우저 요청이 취소/수집 완료/만료된 **410**이면 종료된 요청 문서를 표시하고 승인 폼을 내놓지 않는다. **409**는 거부뿐 아니라 다른 브라우저의 동의가 앱 수집을 기다리는 경우도 있으므로 '이 브라우저에서 동의 불가'로만 안내해 서버 취소를 단정하지 않는다. 브라우저 동의를 받았지만 아직 앱 수집 중인 소유자 화면에서는 그 번호와 '앱의 새 번호와 다르면 이전 요청' 안내를 유지한다.
- 실제 Chromium 관리 브라우저에 390px 두 흐름을 추가한다. ① 취소 요청이 서버에 안 도착 → 예전 페이지 직접 취소 → 새 번호 확인/역할·채널 직접 승인/새 승인 수집; ② 서버는 취소했지만 응답 유실 → 옛 페이지 종료 확인 → 새 번호 직접 승인/수집. 둘 다 원래 송출 PC·다른 creator·캠페인/URL 보존을 SQLite로 비교한다. 네이티브 WinHTTP/WebView2 회귀는 승인 중지 후 '연결 유지'를 다시 체크해도 새 브라우저 요청을 요구하고, 확인/미확인 옛 번호 행과 새 현재 번호를 각각 검증한다.
- 실제 승인 URL은 여전히 시스템 브라우저 전용이고 네이티브 HUD는 공개 확인 코드 외 비밀·verifier·세션 ID를 표시하거나 저장하지 않는다. 게임 PC OBS, WGC 전환, Capture affinity/검정 중지, 광고·회계·HP, 서버 DB·의존성·CI 판정/시간 제한은 바꾸지 않는다.

- 최초 구현 `a6ef0df410112ebe5d9f8f7133d8cd251dd0e1a3`: CHZZK #71에서 기존 플랫폼 타입/서비스는 통과했으나 새 Chromium에서 **서버 fixture 순서 오류**로 실패했다. 실제 "취소 요청 → 새 로그인" 순서와 고정 명령 진단은 `24a7b734`/`a076f004`에 반영했다. CHZZK **#73**에서는 새 Chromium **18/18**을 포함해 전체 성공했고, #74는 변경된 409(거부 또는 타 브라우저 수집 대기)를 오래된 "요청 종료" 문구로 비교한 기존 단위 검사 때문에 **325/326 실패**했다. 기존 테스트도 409 의미를 정확히 검사하도록 수정한다.
- 브라우저 409 표현 개선 `97821dfce4f73dfb3e3c2ac4c44946e8cc269a50`: **410은 취소·수집 완료·만료**, **409는 다른 브라우저 수집 대기와 거부의 구분 불가**로 안내한다. 관련 Chromium은 #74에서 성공했으나 플랫폼 전체는 위 단위 검사에서 실패했다.
- 원래 네이티브 변경의 **Windows #402/run `38729137146`, job `116402349135`: MSVC 빌드 성공, CTest 42/44·218.45초로 실패.** Companion launch는 영상 미검증 경고가 실제 panel client 아래로 벗어났다. 원인은 `CreateWindowExW`에 새 높이를 쓰고 후속 DPI-scaled `SetWindowPos`에서 옛 높이 722/666을 다시 적용한 것. `native-display-client`는 '취소 미확인'으로 바뀐 UX 문구와 이전 단위 검사 문구의 불일치이며 게임/송출 기본 시나리오와 취소 확인 시나리오는 통과했다. **하나의 dialog_height를 생성과 DPI 적용에 재사용**하고 두 역할의 하단 미검증 경고가 client 안에 있는지 실 HWND로 검사한다. 실패를 CI timeout 조정으로 숨기지 않는다.
