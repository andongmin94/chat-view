# Companion window-video output

The experimental G3-03 path extends the existing companion, not a qualified capture-card or dual-PC broadcasting product. [PRODUCT.md](../PRODUCT.md) owns the goal; [development-plan.md](development-plan.md) owns results and remaining work.

## Select, identify, then start the game

Run the HUD with `--companion`. Its privacy warning remains. **Ctrl+Alt+Shift+C** opens chat; **Ctrl+Alt+Shift+V** opens **게임 창 별도 출력 (실험)**. These are two explicit ways to open the *same* protected chat/video panels on the one gaming companion. The native chat button queues a same-thread UI-only registered message, which the existing video panel receives; the streaming/OBS-managed chat role has no such video button. Neither changes the target, current test-pattern consent, output mask or chat approval. The output panel presents the current local video step separately from detailed notices: **1/5 select a game window and separate SDR extended output**, **2/5 paint a synthetic identification pattern**, **3/5 inspect and explicitly confirm the receiver pattern**, **4/5 wait under a black cover for a fresh selected game frame and then output it**, **5/5 stop to the independent black cover**. The numbers guide a user; stage text never grants new capture consent or asserts a receiver has verified an image. When an old source is invalidated, a black output needs refreshed choices, not a silent restart. The stop stage distinguishes an intact black cover from unknown cover protection and instructs stopping the receiver if protection cannot be confirmed. The companion panel's **자체 채팅 연결창 열기** action does not advance video stages, consume a painted pattern or touch the black cover; the native connection and video pipeline remain independent. Its success/refusal feedback stays next to the chat button, not in the video notice: the active test-pattern label must remain readable throughout the receiver's visual confirmation, and the running/black-cover notice must not be replaced by a chat-open result.

Select a visible external top-level game window and a separate non-primary SDR extended display. Neither choice is preselected or saved. The list excludes this process's windows, desktop/shell and hidden/minimized/cloaked windows. Source process/thread and visibility are rechecked before either the pattern or capture can begin.

The selected output shows only synthetic color bars, a full inset border, a random six-character visual label, dimensions and an elapsed-seconds/moving marker. The same label appears read-only in the control panel. This stage does not start WGC or capture game/HUD pixels. It contains no game title, private chat, account, login token or enrollment identifier. There is no code-entry field, copy/paste pairing or remote registration. The pattern itself may be visible in a receiver's live program, so use a test/preview scene, not a live audience feed.

On the receiving PC, inspect the same label, complete border and moving marker. Choose **2. 수신 확인 · 게임 출력** and explicitly confirm. The default remains No. This is the user's visual check, not an automated receiver acknowledgement or proof of cabling, clean video, latency or advertising exposure. It does not set `captureState` to verified or write account/audience evidence.

Only a successfully painted, still-current pattern for the same selection generation permits that transition. The existing confirmation dialog keeps its default-No, selection-generation and topology checks. The worker-start boundary consumes the current pattern once, immediately before masking and capture start; an expired, missing or previously consumed check cannot start capture through that boundary. The existing output and cover HWNDs remain in place: the pattern becomes black first, then the existing WGC engine starts, and fresh game frames replace black when ready. There is no intermediate destruction of the output window. Cancelling confirmation keeps black and requires a new pattern before another attempt.

Patterns expire after two minutes on the existing UI clock/timer. Selection changes, refresh, stop, window close requests, session/power/display/device interruptions and invalid topology invalidate the check and mask it black. A context change while the modal confirmation is open invalidates that consent even if conditions subsequently recover. Already-queued timer messages cannot resurrect a reset check; [KillTimer alone does not remove queued WM_TIMER messages](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-killtimer). Recovery never confirms or starts video automatically.

The user configures OS displays and physical cabling. ChatView does not reconfigure monitors, clone the primary display, run an OBS projector or install another broadcasting suite. Game, HUD and controls must not overlap the output. Active display-path queries reject clones, advanced color/HDR and unknown topology. While checking or capturing, geometry is checked on each UI tick and active SDR paths at most once per second. Output/cover geometry and the selected GDI display name must still match; failure stops rather than choosing another screen.

## Interruption and explicit release

**중지 · 검은 화면** resets any visual check, cancels its timer, signals capture cancellation and raises/repaints the independent owned black cover without waiting for GPU teardown. The private HUD remains available under its existing policies. Stopping a still-valid target retains its selection and output binding, including while it is resizing. After the worker has stopped, choose a new **1. 시험 패턴 표시**, inspect it on the receiver and confirm **2. 수신 확인 · 게임 출력** to resume on the same output and cover. Source resizing or a late capture report does not restart a stopped output or replace its new pattern. Target loss, capture failure and interrupted topology instead require refreshed choices and new selection. A different output cannot implicitly destroy the old black window.

The panel registers current-session [WTS notifications](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsregistersessionnotification); failure prevents video controls opening. Lock/disconnect, unlock/connect, suspend/resume and display/settings/device-list changes stop in the handler and invalidate target lists. Refresh and manually select/identify again. Device-list notifications lack a specific identity, so unrelated device changes may conservatively interrupt output too. Existing HUD lock/protection behavior is not weakened.

**출력 창 닫기** first stops to black and asks whether use of this input has been stopped on the receiver. The default is No. Declining retains black rather than resuming capture. A context change cancels pending release. Confirmed release destroys HWNDs only after the worker finishes. ChatView cannot verify the receiver was stopped.

A later **중지 · 검은 화면** command received before that destruction cancels the pending release as well as capture. Cancellation is latched before synchronous cover painting can dispatch owner messages. The same black HWNDs and still-valid target remain; resuming requires a new pattern and confirmation, not the cancelled release consent. The panel distinguishes pending release, cancellation and completed release. This is not an undo after the windows have been destroyed, a guaranteed cancellation window, or protection after app exit. A confirmed release not superseded by Stop still closes normally after worker completion.

App exit, crash or confirmed release can expose that display's desktop. A topmost window does not control other programs, cursor/system overlays, secure desktop or HDMI after process exit. Failure to raise/paint the cover is reported as unconfirmed protection with an instruction to stop the receiver's scene, not success.

## Windows/GPU boundary

The engine uses [CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow) and `GraphicsCaptureSession::IsSupported`. Only the selected external window is captured. No desktop fallback, hook, driver, hidden OBS, encoder, audio or network-video service is added. The system capture border stays enabled.

A worker owns hardware D3D11, free-threaded WGC, a two-buffer pool, DXGI and D2D scaling. Callbacks only signal that worker. The newest bounded frame is preferred; frames/window titles are not logged or persisted. SDR BGRA dimensions are at most 4096 each, with aspect-preserving black letterboxing. Every frame's ContentSize is checked against the actual D3D texture allocation, not just the last requested pool size. Only ContentSize is copied because [pool padding can be undefined](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture).

Pool capacity starts at the selected window's size and retains the largest observed width and height independently until capture stops. Shrinking or returning to a size within that capacity does not recreate the pool or discard pending frames. ContentSize still determines the exact copied rectangle and output aspect ratio, not the retained allocation. Only growth beyond requested capacity reallocates the frame pool, with the per-axis maximum of existing capacity and new content. A complete, fresh transition frame is presented before normal Recreate; an incomplete growth frame is never presented and instead causes retirement of the old capture pool and creation of a fresh pool/session on that same item. All checked-out frame/surface references are released before either operation discards pending frames.

A clipped frame is never copied. Growth beyond capacity stays black in Waiting while larger buffers are requested. When the one available frame has content larger than its old surface, Recreate discards that frame; the worker closes and restarts the capture session **on the same selected GraphicsCaptureItem** after resizing the pool, to request a fresh initial frame even for a one-paint static source. This is not a new target selection or recovery after source loss. If a late smaller surface arrives after sufficient capacity has already been requested, it is discarded without recreating the same capacity or repeatedly restarting the session. A static source can still wait for new WGC content; the engine never asks the source to redraw or invents a fresh timestamp. The two-buffer and 4096-per-axis bounds remain; a larger allocation can remain after shrink until normal worker teardown. This is not a resource-soak qualification. Capture stays on the same selected window and output; a size change is not new target consent or permission to recover a lost window.

The synthetic identification pattern is a small GDI renderer on the independent cover HWND, never GDI over the DXGI flip surface. It accepts 160x120 through 4096x4096 rectangles, scales its layout/font, restores selected GDI objects and uses no new package. Invalid geometry, allocation, timer or paint failure cannot enable capture. It is a wiring-identification aid, not a color-calibration or end-to-end timing instrument. A busy/hung OS is not a hard-real-time expiry guarantee; the receiver must inspect motion.

Minimizing, hiding, closing, cloaking or identity loss terminates capture. The worker maps WGC's QPC-based SystemRelativeTime to a conservative local content timestamp, rounding age upward, and rejects content at the two-second boundary. It checks again after presentation and any pool recreation and never substitutes GPU completion time for original content time. Stop, error and teardown invalidate that timestamp. Content geometry changes invalidate it before GPU work even when capacity is reused; only a successfully presented, still-fresh frame can publish its original content time again. A slow GPU operation therefore cannot report an old frame as newly captured just because the call returned.

The HWND owner separately applies the same two-second content-age limit on its existing tick, even while the worker's last status still says Capturing. Missing/future/stale timestamps keep the independent cover black; the owner does not wait for the worker to change status or finish clearing. Fresh content can uncover the same still-running selection after transient waiting. After explicit stop, invalidation or shutdown, even a late fresh snapshot cannot uncover it. Static windows may still go black until new frames arrive. This is a local UI/worker boundary, not a guarantee under a stalled UI/OS, a hung driver that prevents composition, or a physical HDMI receiver.

Final close keeps HWNDs alive through GPU teardown. [DXGI may synchronously send owner-thread messages](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/dxgi-best-practices), so the shutdown wait services sent messages rather than using a plain blocking join. Reentrant starts are fenced; posted input/commands and WM_QUIT are not consumed. Driver/OS teardown is not guaranteed hard real-time; there is no detached-worker/use-after-free timeout fallback.

## Verification boundary

Existing geometry, companion, WGC pixel and shutdown-wait cases remain. The portable check test covers first-paint gating, two-minute boundary, clock/generation changes, stop, single-use confirmation and identifier formatting, plus content-age conversion, exact expiry, missing/future timestamps and slow-presentation aging. The native lifecycle test checks synthetic GDI colors/border/motion, actual cover pixels, no game capture during identification, a consumed check before real WGC transition, reset/expiry and notifications, alongside previous release/reuse/active-close cases.

That fixture mounts a synthetic rectangle on one desktop through friendship. Its pattern timer is disabled inside the fixture to avoid treating that rectangle as a real second monitor. Notifications and queued-timer rejection still pass through the real WndProc. The positive transition uses test friendship for the topology/human-consent boundary, but the production worker-start function consumes the check and the production snapshot handler controls the cover; it does not claim that a physical receiver or two-monitor consent path was exercised. The stale-frame regression feeds old/missing/future snapshot timestamps into the actual owner-side handler while a real GPU output is running, verifies black pixels and then restores a real fresh snapshot. It does not hang the driver. Product selection has no topology override. Unavailable interactive environments fail rather than skip.

The panel lifecycle flow resizes the synthetic source, sends the actual Stop command during a resize burst and requires immediate cancellation intent, the same HWNDs, a visible independent cover and nine black output samples. It changes source content while stopped and replays late status separately as synthetic input. A new pattern must not start WGC; subsequent confirmation must reveal distinct fresh content with the new aspect ratio and black bars on the same HWNDs, then continued animation. Tests do not start the worker directly or hide the cover to manufacture a pass. This is an actual HUD/panel/WGC/GPU fixture with synthetic output placement and consent, not a full physical companion/receiver acceptance test.

The same lifecycle fixture accepts the actual default-No release dialog, delivers Stop before the destruction tick and verifies cancelled release, retained source/HWNDs, nine black pixels, late-status/timer rejection and fresh WGC pixels after a new pattern. The pending flag is set by the production dialog handler, not injected. This orders reachable UI commands deterministically; it does not simulate a driver hang or guarantee time for a human to cancel an already completed release. Existing declined/context-invalidated and normally completed releases remain in the suite.

The WGC test retains its original first-frame and resize assertions and time/color bounds. Its resize flow connects received/presented dimensions and freshness to real output pixels: width growth, a static portrait shrink painted once, resumed animation, mixed width/height changes and continued capture on the same HWNDs. Twelve further static generations cover alternating aspect ratios, odd dimensions, A-B-A, same-size new content and immediate intermediate redraw bursts. Unique generation colors, nine interior samples and black-bar samples reject old/intermediate content and leftover padding. Pool-capacity and exact recreation-count assertions require reuse within capacity, not just an eventual pixel pass. Existing output resizing, minimize, stop, restart, close and visible-HUD assertions remain. The first-frame ten-second, per-resize five-second, RGB tolerance eight and whole-test forty-second limits are unchanged. The portable layout test separately covers completeness, growth, reuse, late clipped surfaces and bounds; it is not native WGC evidence.

Test diagnostics report fixed synthetic pixels, last received/presented/surface sizes, requested pool capacity, status/frame count, recreation/clipped counts, a failure HRESULT and whether output is topmost at a fixed point. These independently sampled counters are not a transactional frame snapshot or production image logger. No screenshot, window title, private chat or account data is persisted. A later successful run alone does not resolve a prior intermittent failure.

Physical two-display/capture-card/encoded receiver video, game/anti-cheat/protected surfaces, multi-GPU, latency, audio, prolonged resources, real lock/resume/hotplug and overlay exclusion remain hardware acceptance work. Exact executed checks and failures are recorded only in the development plan.
